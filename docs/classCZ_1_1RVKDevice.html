Command streams (RVKPainter)

Each thread records its consecutive passes into a single command buffer (its stream) instead of one per pass: each command buffer costs the driver a reset and a submission entry. The stream is queued (see enqueueCommand()) by its thread before any other submission of that thread (present, uploads, readbacks, Skia, wait()...) and by RVKCore::clearGarbage(), or by another thread needing a sync made while it was open (see resolvePoint()).

Detailed Description

Vulkan backend implementation of RDevice.

Wraps a single VkPhysicalDevice/VkDevice and its graphics queue, and owns the resources shared across the backend: the painter pipeline cache, per-thread Skia (Ganesh) contexts, a queue mutex serializing submissions, and a fence-tracked deferred-destruction queue enabling asynchronous, non-blocking command submission.

Obtained by downcasting an RDevice via RDevice::asVK().

Submits an already-recorded command buffer signalling fence, consuming pending waits, WITHOUT blocking. The caller tracks completion via fence (typically pairing with deferDestroy() so CPU/GPU can pipeline). Used by RVKPainter::flush.

Owned pending-wait semaphores consumed by this submission are appended to ownedWaitsOut; the caller must destroy them once fence signals (e.g. inside its deferDestroy cleanup).

If signal is not VK_NULL_HANDLE it is signalled on completion (e.g. a swapchain present semaphore that vkQueuePresentKHR waits on), so present need not block the CPU.

◆ enqueueCommand()

bool enqueueCommand ( VkCommandBuffer cmd,
std::function< void()> cleanup,
VkSemaphore signal = VK_NULL_HANDLE ) const
noexcept

Queues a recorded command buffer for the next batched submission.

Each vkQueueSubmit is a driver and kernel round trip (validating every buffer object), and a frame records many passes (e.g. the blur chain), so they are sent together, in the order they were queued. Any other queue submission (immediateSubmit(), submitSignal()...), a present, a Skia submit, wait() and exporting or CPU-waiting a sync of this device send the batch first, so the queue order seen by the GPU stays the recording order (see also flushStaleBatch()).

Parameters
cleanupRuns on this thread's clearGarbage() once the GPU finished the command buffer.
signalSignalled after it (e.g. a swapchain present semaphore): the batch is sent now.
Returns
false if the batch was sent and failed (the cleanup still runs).
